# Hosted MCP operations

**Obsolete release:** `hosted-mcp-review-20261016`, commits `8e7bd8f`/`fa3ca67`, and both earlier review bundles predate the upstream bridge integration. Do not install them: their migration 15 collides with the bridge migration. Use the integrated schema-16 revision.

This change implements remote MCP. It does not itself deploy or enable it. The current production endpoint must not be described as live until deployment, enablement and a real authenticated check are completed.

## Architecture and credentials

`Agent → HTTPS /mcp → Caddy → Bun 127.0.0.1:8082 → Rust private Unix auth socket → Rust REST 127.0.0.1:8080 → notebook`.

The agent sends its own expiring `tsmcp_…` credential. Rust exchanges it for a request-specific REST delegation; no global REST token is configured in Bun. Direct REST use of the MCP credential is rejected. Credentials are managed in hosted Settings → Access → Agent connections, using the signed-in operator session. The normal default is read only for 30 days. Secrets appear once and must go in the client's secret store, not a URL, repository, chat transcript or command history.

Endpoint: `https://studio.tan.coffee/mcp` (exact path, no query).
Transport: Streamable HTTP, POST with JSON and Accept `application/json, text/event-stream`. SDK 2.3.1 supports modern 2026-07-28 and stateless legacy 2025-11-25. Clients should let their MCP SDK supply protocol headers/metadata. No `/sse` endpoint. Authenticated GET and DELETE receive 405. Custom bearer authentication only; OAuth-only connectors cannot connect yet.

Read tools: `tan_status`, `tan_list_pantry`, `tan_search_profiles`, `tan_search_coffees`, `tan_search_roasts`, `tan_get_context`, `tan_get_roast`, `tan_list_attachments`.

Write permission adds: `tan_create_coffee`, `tan_update_coffee`, `tan_update_roast`, `tan_record_brew`, `tan_update_brew`, `tan_add_note`, `tan_set_profile_image`, `tan_create_label`.

Resources: `tan://pantry`, `tan://device`, and `tan://profiles/{id}`, `tan://coffees/{id}`, `tan://roasts/{id}`, `tan://brews/{id}`. Both placements also expose one `tan_api_*` tool per versioned OpenAPI operation. These tools use complete REST schemas and exact storage units. Read-only grants expose only GET operations. The API still checks operator-session permissions for credential and bridge administration. The local stdio service keeps its file-upload and device-sync helpers.

## Build and review (no production changes)

Run `bun install --frozen-lockfile`, `bun run check`, then `./script/build_hosted_release.sh <version>`. Docker builds web/JS on the native builder and cross-compiles Rust for Linux amd64, avoiding Apple Silicon x86 emulation failures. The output contains the Rust service, web assets, Bun 1.4.2, HTTP adapter, optional routing, systemd unit and enable/disable scripts. The checked-in dist bundles are regenerated by `bun run --cwd plugins/tan-studio build`.

Validate Caddy using the deployed Caddy version, with both the absent and present optional include. Verify backup restore procedure and disk space before any production installation. Do not include user secrets in a release or review bundle.

## Deployment and enablement (separate approvals)

1. Obtain approval for the concrete release deployment. Use the existing hosted release installer. It snapshots the notebook, upgrades to schema 16 and preserves any previously explicit MCP enablement; a first deployment leaves MCP disabled.
2. Confirm the Rust health endpoint and UI remain healthy. Inspect the release artifacts and migration backup. On first rollout, do not point the current symlink back at a schema-15 binary.
3. Obtain explicit approval to enable the public authenticated endpoint. On the VM run `sudo /opt/tan-studio/current/enable_mcp.sh --enable-public-mcp`. This provisions the non-login Unix service identity, private socket directory, Rust drop-in, MCP unit and Caddy include. It creates no agent credential.
4. Verify local `/readyz`, public unauthenticated `/mcp` returns 401 with a bearer challenge, forbidden origins return 403, nested `/mcp/*` and `/internal/*` return 404, and the web UI still works. Confirm service logs contain no bearer values.
5. With approval for the specific agent's persistent access, use Agent connections to create one read-only credential with a suitable expiry. Select write access only if that agent is authorized to mutate the notebook. Configure and test the actual client/version, then verify revoke and replacement rotation. Do not grant access merely to perform a smoke test without approval.
6. Check memory and request latency on the e2-micro with backups running before treating the release as operationally validated. Initial limits: 256 KiB request, 1 MiB response, 20 seconds, 4 active requests per agent, 16 globally; token buckets 60 requests/min per agent (burst 10), 30/min per source IP (burst 30).

If enablement fails, inspect `journalctl -u tan-studio -u tan-studio-mcp`. A readiness failure leaves the public route absent on first activation. Do not paste credential-bearing request logs into diagnostics.

## Client configuration

For a client that accepts a URL and custom headers, configure:

```json
{
  "url": "https://studio.tan.coffee/mcp",
  "headers": { "Authorization": "Bearer <agent credential from secret store>" }
}
```

This is a generic descriptor, not a promise of a particular client's configuration syntax. The actual agent platform was not selected during implementation. Map its header/secret-store fields to this descriptor. Do not use the existing REST API token, Google token, operator cookie or a shared credential.

With the pinned official TypeScript client:

```ts
import {
  Client,
  StreamableHTTPClientTransport,
} from "@modelcontextprotocol/client"
const client = new Client({ name: "my-agent", version: "1" })
await client.connect(
  new StreamableHTTPClientTransport(new URL("https://studio.tan.coffee/mcp"), {
    requestInit: {
      headers: { Authorization: `Bearer ${process.env.TAN_MCP_TOKEN}` },
    },
  })
)
const tools = await client.listTools()
await client.close()
```

Keep the credential outside source control. First exercise a read tool. A stale revision returns the REST conflict unchanged. A timeout/disconnect on a mutation may mean it committed: fetch current data before considering another write. Request IDs are not idempotency keys.

## Disable, rollback and rotation

To remove public MCP while retaining the notebook, after approval run `sudo /opt/tan-studio/current/disable_mcp.sh --disable-public-mcp`. It removes optional routing, stops/disables Bun and removes Rust's MCP drop-in. Existing credential rows remain stored and can still be revoked from the operator UI. Disabling alone does not revoke credentials; if re-enabled, unexpired non-revoked credentials work again.

For a code rollback after schema 16, keep a schema-compatible Rust release and disable MCP. An older binary refuses the newer schema. The installer now refuses automatic downgrade when startup migrated the notebook. Restore a pre-deploy snapshot only through a reviewed recovery procedure with the service stopped, after explicitly accounting for writes since the snapshot. Never silently replace the live database.

Rotate by creating a replacement, switching the specific agent, verifying a read, then revoking the old credential. Revocation invalidates even previously issued REST delegations at their next authorization check. Rust restart invalidates all short-lived delegations but preserves the long-lived agent credentials.

## Isolated native runtime verification

Build and run the dedicated verification image on the host's native Linux architecture:

```sh
docker build -f deploy/hosted/Dockerfile.verify -t tan-studio-mcp-verify .
docker run --rm --pull never --network none tan-studio-mcp-verify
```

The image publishes no ports and mounts no host files. Dependencies are fetched at build time; execution has no external network. It runs the MCP tests and the complete Rust suites, including hosted bridge tests and the schema-15-to-16 upgrade test. The integration fixture creates a temporary notebook, three temporary credentials and a private Unix auth socket, then starts the actual bundled `http-server.js` child process. The official client connects over loopback HTTP and checks catalog permissions, writes, reads, attribution, revision conflicts and MCP-versus-REST audience isolation. Readiness and unauthenticated 401 behavior are checked too. Fixture credentials are never production credentials.

On Apple Silicon this is native Linux ARM64, not validation of the AMD64 release binary. To validate that target, run the same commands on a non-production native AMD64 host (for example a dedicated Debian 13 test VM with Docker). Do not run the fixed-port bundled fixture directly on a shared host. The default macOS fixture instead chooses ephemeral loopback ports and uses native Bun.
